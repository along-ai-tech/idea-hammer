description: product-spec 0-1 模式工作流。Phase 划分，从用户初次表达到生成 Product-Spec.md。
---

[使用时机]
    项目里没有 Product-Spec.md，用户第一次表达想做产品。

[顶层规则]
    需求工程五层是主线：PRD（为什么做 / 为谁做 / 什么价值）→ FRD（每个功能怎么工作）→ User Story（需求表达方式）→ AC（可验证的完成条件）→ Spec（组织成可执行规格）。Phase 采访按层补齐，生成时按模板分层落位。
    每个 Phase 达到出口判据才解锁下一个，Phase 1 到 3 是地基。
    允许渐进式：用户初始描述里已覆盖的维度直接吸收并复述确认，不机械重问。
    形容词永远不算合格答案，逼出具体见 references/interview-principles.md 的四把刀。
    每相位结束默扫 interview-principles 的反失败自检。
    Phase 标签不暴露给用户，用承上启下的人话过渡。
    详细问法见 references/question-bank.md 对应 Phase。
    分级采集：地基字段（问题、job、范围优先级、任务、数据模型、功能行为、非功能、验收）问到底；细节字段（token 具体值、文案细则）标 [待补充] 交设计和 dev。
    编号纪律：生成时给 TASK / FLOW / REQ 等编号，供 Design Brief 的 SCREEN / CMP 跨文档引用；两份文档的 P0 内容保持一致。
    产品类型识别：Phase 0/1 判断产品本身是不是 agent / 自主系统（用户给目标、系统自主执行），是则在功能之后解锁 Phase 8 agent 专项。

[Phase 0 · 主线：一句话入口 → Discovery → 引导补齐 → Spec 成稿]
    0-1 模式的主线只有这一条，不分岔：
        [第一段 · 入口] 无论用户给一句话还是一段话，都先走 idea-intake 五步：
            拆句成候选能力 → PRD 七要素盘点（有 / 模糊 / 缺失）→ 技术与风控未知 → 建议范围与指标 → 假设 / 开放问题。
            输出"缺什么"的清单，不是半成品 PRD。
        [第二轮 · Discovery 前置层] 只问值不值得投入，不展开用户场景（product-definition 第一轮）：
            D1 为什么做（业务问题 + 损失）/ D2 为谁做（哪些用户真正需要）/ D3 价值类型（增收 / 降本 / 降风险）
            / D4 为什么现在（紧迫性对比）/ D5 值得投入吗（投入量级 + 更便宜的替代方案）
            边界：不问市场规模、变现预测、定价；可以估投入量级与替代方案，不做 TAM/SAM 测算。
        [第三轮 · 引导补齐] 按缺口跑 product-definition 第二轮 5 问，只问缺失 / 模糊的维度：
            Q1 场景与卡点（追问不做的代价）/ Q2 现有凑合做法 / Q3 解决后的价值 / Q4 第一版范围（非目标可标 [待定]）/ Q5 怎么算做成。
            Q1–Q3 是目标层，必须用苏格拉底式追问（principles/socratic-questioning.md）：澄清 → 检验证据 → 找反例 → 推后果，一次只问一层；
            不接受"更高效 / 所有人都需要"这类回答，必须落到具体人、具体场景、具体数字。
            每问答案当场落进对应 Spec 字段，不另记笔记。
        [第四段 · Spec 成稿] 按模板五层组织，过出口判据：下游能否直接排任务、写代码。
    分轮铁律：Discovery 与场景追问不在同一轮里混问；Discovery 没结论，不进入 Q1。
    硬门禁（每问结束都做，不等最后）：
        对照 spec-standard 四要素检查 PRD / FRD / User Story / AC；每发现一处缺失或不确定，当场三选一：
            变成具体追问（≤ 3 个阻塞）/ 写进 §10.1 假设（带依据与猜错后果）/ 写进 §10.2 开放问题（标阻塞）
        禁止带 [待补充] / {{占位}} / TODO 进入下一 Phase。
    Discovery 出口（第一轮结束）：
        业务问题真实存在、价值可归因（增收 / 降本 / 降风险）、投入合理（有替代方案比较）三条同时成立 → 进入第三轮；
        任一不成立 → 明确告诉用户"现在不值得做"并记录理由，停止或转向，不硬生成 Spec。
        D2 / D4 不达标不阻塞，但必须写进 §10.1 假设或 §10.2 待确认。
    出关校验：python3 scripts/check_spec_standard.py --project <项目目录>
        不通过 → 不准进 Design Brief / DEV-PLAN，回到缺口对应的追问或假设。
    搜索增强第一遍：进场前 WebSearch 竞品和行业，带具体例子进场，质问才有据。
    先听用户开放描述，从里面抽取已表达的维度复述确认，不让他重复回答已说过的。
    答不了的进 Spec §10.1 假设 / §10.2 待确认，不替用户编答案；一次最多 3 个阻塞问题。
    不做市场规模（TAM/SAM）与变现预测，不追问定价；Discovery 只判断投入产出是否合理、有没有更便宜的替代方案。

[Phase 0.5 · 产品类型判断（扫描路由开关）]
    走 competitive-scan 的 [项目类型判断]：业务参照型 vs 市场机会型。
    判断三问（任一为是 → 业务参照型）：公司已有业务方向 / 行业有公认成熟方案 / 用户主动说"参考 XX"。
    否则默认市场机会型。
    落进 Spec 0.5 字段。生成 Spec 前主 Agent 必须向用户确认类型（"我把它当 X 型，你看对吗"），未定不能继续 Phase 1.5。
    出口判据：用户点头说"对，就是 X 型"。
    类型决定 Phase 1.5 / 1.6 / 1.7 的填充权重与跳过阈值。

[Phase 1 · 问题与人，地基]
    覆盖：真实问题、唯一主用户、现状 workaround、痛的代价。
    出口判据：能复述"谁、什么问题、今天怎么凑合、这事值多少"，用户点头。

[Phase 1.5 · 行业标杆参考]
    先按 0.5 产品类型路由：
        - 业务参照型：≥ 2 同类产品（仅作参考），替代方案可豁免，重心转向 Phase 1.6。
        - 市场机会型：≥ 2 同类产品 + ≥ 2 替代方案（含非同类工具/土办法），三列必填。
    走 competitive-scan Part 1 全文（看不到直接同类产品本身是信号，照样要走）。
    目的不是判断"我们凭什么赢"，而是看清别人怎么把功能做出来：
        契合点（对应我们的哪个需求）/ 需定制点（借过来要改什么）/ 原创点（它没做好、必须自己设计）。
    填入 Spec 模板 1.7 节。
    出口判据：能逐行说清"它的关键机制是什么、对我们哪个需求有用、要改什么、哪块必须原创"。

[Phase 1.6 · 行业借鉴]
    先按 0.5 产品类型路由：
        - 业务参照型：≥ 3 优秀做法（硬性下限），必须落在本公司业务场景里说清怎么用——本节是价值核心。
        - 市场机会型：≥ 2 顶级品类优秀做法（仅顶级品类，避免被细节淹没差异化），差异化风险列可不填。
    走 competitive-scan Part 2 剩余纪律：每行"我们怎么用"必填，必须说"要 / 不要 / 改造后用"，落到我们哪块场景；不许写"可以参考"。
    填入 Spec 模板 1.8 节。同一产品可在 1.7 / 1.8 双填，按角色分。
    出口判据：能列出"这块谁做得好 / 我们怎么拿过来 / 拿过来后差异化怎么不丢"。
    跳过条件：迭代模式（小功能改动）默认跳过，仅当用户说"看看行业怎么做"或主 Agent 判断改动方向需要参考时触发。

[Phase 2 · Job 与成功，地基]
    覆盖：无方案的 job 陈述、成功度量、北极星。
    出口判据：一句不含任何方案的 job，加一个可度量、不可灌水的成功条件。

[Phase 3 · 范围与非目标，必须过]
    覆盖：v1 砍什么、至少 3 条显式非目标、维生素还是止痛药。
    出口判据：有明确的不做清单，加 v1 单一必须功能。

[Phase 3.5 · pre-mortem 反向思考]
    走 question-bank Phase 3.5：3 个失败原因 + 概率最高的 1 个有具体"哪一步崩 + 我提前发现信号"。
    3 个失败原因 + 监控信号进 Spec 8. 非功能需求表（标 P0 监控项）。

[Phase 4 · 任务、旅程与功能]
    覆盖：用户任务 TASK、端到端用户旅程逐步走、每个功能拆到触发→系统→产出加 MUST/SHOULD 规则和输入校验、核心数据模型（实体 / 关系 / 规则）。
    每条 P0 REQ 写 FRD 前，先走 principles/frd-research.md：
        至少 2 个同类产品 + 2 个业界实现 / 标准，只提炼机制不抄实现；来源（名称 / 版本 / 链接 / 日期）随规则或状态记录。
        逻辑严谨自检：状态全覆盖（失败 / 超时 / 重试）、边界与非法输入、并发与幂等、权限与越权、级联与回滚、错误契约、可观测。
        产品层竞品扫描（Phase 1.5 / 1.6）不能替代 FRD 层调研，两者分工见 frd-research。
    用户报竞品时触发搜索增强：再搜那竞品做法追问差异（用于填充 1.6）。
    Phase 1.5 / 1.6 完成后，遇到用户追加新想法或主 Agent 发现可借鉴做法，可回头补 Spec 1.8。

[Phase 5 · AI 能力]
    先 litmus test，再对照 SKILL 的 [AI 能力对照表] 主动告知，每个 AI 功能问全概率性四问，见 question-bank Phase 5。

[Phase 6 · UI 与状态，最易跳过，强制]
    覆盖：布局结构、区域内容、控件，加每个核心界面的加载、空、错误、成功、无权限五态。

[Phase 7 · 验收与边界]
    覆盖：关键功能写成 Given-When-Then、边界值、非功能 6 类（性能 / 安全 / 隐私 / 兼容 / 可靠 / 可访问）给数字、依赖、假设与待确认问题。
    AC 写作标准（principles/spec-standard.md §4）：
        每条 REQ ≥ 3 条，覆盖主路径 / 边界 / 错误；一条只验一个结果；Then 必须可观察；禁用"快速 / 友好 / 合理 / 尽量"等模糊词；
        编号 AC-<REQ>-<nn> 全局唯一，且每条都能被将来的一条 TEST 直接承接。

[Phase 8 · Agent 系统专项，仅 agent 产品]
    仅当产品本身是 agent / 自主系统时解锁。覆盖：自主性与人在回路、工具与能力集、上下文与记忆、编排与多 agent、评估与可观测、成本与预算、失败与卡死、会话与状态，见 question-bank Phase 8。

[完成度判据]
    什么叫够了，三个判据一起看：
    - 交接测试：把 Spec 交给一个没参与对话的工程师，他能直接开工不用猜吗？需要猜的地方就是还没够。
    - 边际测试：再问一个问题，答案会改变要做什么吗？不会，就别问了。
    - 不对称原则：缺了会让开发返工的，地基、范围、关键功能行为、状态，必须问到底；缺了以后便宜能补的，边角样式、二期功能，标 [待补充] 直接放行。
    相位级：能用自己的话复述该相位的 problem、现状 workaround、成功条件、非目标，用户点头，就进下一个，说一句"这块我够了"。
    整体级：关键需求约 80% 置信，剩余都是便宜能补的，就停。完美是敌人，可执行是目标。
    收尾三件套：覆盖清单逐 Phase 过一遍，加元问题"我该问没问的是什么、还该找谁"，加读回结构化摘要让用户纠正。达标才生成。

[收尾 · 多手段审查]
    单一视角必然漏问题，出关前用多种手段交叉验证，结论写进自检报告：
        1. 脚本门禁：python3 scripts/check_spec_standard.py --project <目录> 通过
        2. 追踪校验：python3 scripts/check_traceability.py --project <目录> --strict 通过（后续阶段持续）
        3. 多角色自检：ceo-lens / eng-lens / qa-lens 三顶帽子逐条问，漏项 → §10.2 或当场追问
        4. 反向思考：pre-mortem（Phase 3.5）的失败原因与监控信号是否已进 §8
        5. 目标层复检：Discovery 五问是否有业务问题、价值类型、投入与替代；Q1–Q3 是否有用户原话与具体数字，是否仍有"更高效/所有人"类表述
        6. FRD 复检：每条 P0 REQ 是否有调研来源、状态与失败路径是否齐全
    多角色自检细节：ceo-lens 4 问 / eng-lens 5 问 / qa-lens 4 问；每顶帽子漏掉的事 → Spec 10.2 待确认表或当场追问。
    对齐记录：把 Spec 读回给用户，记录"谁确认 / 日期 / 遗留分歧"到文档元信息，未确认不得进入 Design Brief。
    生成 Spec 时附 3 段 ≤ 5 行的自检报告。

[生成]
    生成前先搜索增强第二遍：按已聊出的核心功能、AI 能力、技术方向再搜一遍当前最佳方案和可行性，让 Spec 的技术选型和 AI 能力是当前的、有针对性的，不是泛泛的。
    按 templates/product-spec-template.md 生成 Product-Spec.md，给 TASK / FLOW / REQ / SCOPE / DEP 等编号，供 Design Brief 跨文档引用。
    输出必须满足 contracts/output.schema.json（四要素必填），不是 AI 自由发挥的散文；生成后跑 check_spec_standard.py 与 check_traceability.py。
    分层落位：PRD 层（§1 背景 / 角色画像 / 核心问题 / 价值 / 指标 / 竞品、§2 功能范围、§3 业务流程、§4 优先级）；FRD 层（§5 每个 REQ 的行为 / 规则 / 输入输出 / 状态）；User Story 写在每个 REQ 里（作为一个…我希望…以便于…）；AC 跟在每个 REQ 后（AC-###-##）。
    只把用户明确说过的写进去，推断的写进假设（带依据和风险），纯空缺标 [待补充]，不凭空补。
    AI 功能按 AI 能力规格填质量条、触发方式、护栏；agent 产品填 Agent 系统规格。
    范围和功能标 P0/P1，确保和 Design Brief 的 P0 内容一致。
    生成后告诉用户读一遍看哪里要改，引导下一步做 Design Brief、设计稿、或 DEV-PLAN。
