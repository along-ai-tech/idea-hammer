# 原则：行业标杆参考

> 竞品扫描的目的不是证明"我们凭什么赢"，而是看清"这件事别人已经怎么做"。
> 输出三样：跟我们需求的契合点、我们需要定制的点、没人做好需要原创的点。

[定位]

    竞品扫描 = phase-discipline "搜索增强双遍" 第一遍（提问前搜种子）的结构化产出之一。
    行业借鉴 = 同一次搜索的另一个产出。两者并行，不互相替代。

    不是写竞品报告 / 行业综述，也不做胜负判断——是看清别人怎么把功能做出来，
    再决定我们哪些直接借、哪些要改、哪些必须自己设计。

[项目类型判断 · 路由开关]

    在 Phase 0 产品定义之后、Phase 1.5 之前判一次，落进 Spec 顶部产品类型字段。
    后续 Phase 1.5 / 1.6 / 2 范围 / 1.7 / 1.8 的填充权重由这个字段驱动。

    类型 | 含义 | 典型场景 | 扫描重心
    ---|---|---|---
    业务参照型 | 公司/团队已有业务方向，问题域成熟，做法已被验证 | 智能客服、电商上架流程、内部审批系统、ERP 改造 | 学方法：1.7 仅作参考（≥ 2 同类产品），1.8 重点（≥ 3 优秀做法必填）
    市场机会型 | 用户痛点未充分满足，市场窗口未定型 | 宠物节日定制 OPC、新兴 AI Native 工具、垂直 SaaS | 看做法：1.7 必填（≥ 2 同类产品 + ≥ 2 替代方案，三列齐全），1.8 选填（≥ 2 顶级品类优秀做法）

    判断三问（任一为是 → 业务参照型）：
        1. 公司是否已有明确业务线，这次是做业务内部的某个工具/流程？
        2. 行业是否已存在公认的成熟方案（"行规"、"标准流程"），目的是适配本公司场景？
        3. 用户主动说"参考 XX 公司做法"、"按行业最佳实践来"、"适配我们公司"？

    否则默认市场机会型。

    写进 Spec 时由用户确认 / 调整。主 Agent 不要单方面猜类型，猜了要问一句"我把它当 X 型，你看对吗"。

## Part 1 · 标杆扫描（看别人怎么做）

[纪律]

    1. 同类产品（≥ 2 个）
        - 已经在做同样事的产品
        - 不要求全查清——但要能说清"它这个功能的关键机制是什么"
        - 找不到同类产品本身是信号（市场可能没需求 / 或你是第一）

    2. 替代方案（≥ 2 个）
        - 用户**今天**用什么替代解决（Excel / 微信群 / 纸笔 / 求同事）
        - 替代方案往往比同类产品更能暴露真实用法

    3. 三列必填（替代"我们凭什么"）
        - **契合点**：它的哪个做法正好满足我们的哪个需求？引用 REQ / SCOPE 编号
        - **需定制点**：哪些做法可以借，但要按我们的场景改什么？
        - **原创点**：它没做好 / 没做、我们必须自己设计的部分；写"无"要说明为什么不需要

[按类型加权]

    业务参照型：≥ 2 同类产品（仅作参考），重心转向 1.8 行业借鉴。
    市场机会型：≥ 2 同类产品 + ≥ 2 替代方案，三列齐全且契合点要能对上具体 REQ。

[Spec 模板 1.7 节填充]

    | 类型 | 名字 | 解决什么 | 它的做法（关键机制） | 契合点（对应我们的需求） | 需定制点 | 原创点 |
    |---|---|---|---|---|---|---|
    | 同类产品 | A | | | | | |
    | 同类产品 | B | | | | | |
    | 替代方案 | C（Excel/微信群/...）| | | | | |
    | 替代方案 | D | | | | | |

[不接受的答案]

    - "市面上没有竞品"——第一反应一定是错的，回去重搜
    - "它做得很好" / "体验不错"——要写具体机制，不写评价
    - 只列产品不填三列——看了不等于想清楚怎么用
    - "我们比它更好"——这是胜负判断，不是本节要的东西
    - 只列同类产品不列替代方案——替代方案暴露真实用法（业务参照型可豁免，因替代方案就是上一代内部系统本身）

## Part 2 · 行业借鉴（吸收优秀做法）

[纪律]

    1. 借鉴对象（≥ 2 个）
        - 同品类或相邻品类的优秀产品/做法，不必是直接竞品
        - 选的是"某一块做得好"，不是"整体像它"
        - 跨界做法也允许——游戏化来自游戏、协作范式来自飞书/Notion

    2. 借鉴维度必选其一
        - 交互范式（怎么操作 / 信息架构怎么组织）
        - 增长机制（拉新 / 激活 / 留存 / 变现的招数）
        - AI 能力用法（怎么把 AI 嵌进去、怎么避坑）
        - 工程实践（性能 / 稳定性 / 可观测的成熟方案）
        - 商业模式（怎么收费 / 怎么续费 / 怎么扩客单）
        - 任意其他能让 Spec 更聪明、减少发明轮子的维度

    3. "我们怎么用" 必填
        - 每行都要写"我们要 / 不要 / 改造后用"
        - 不许写"可以参考"——必须说出具体落地："把 X 的 Y 用到 Z 场景，但要避开它的 W 问题"

[按类型加权]

    业务参照型：≥ 3 优秀做法（硬性下限），必须落在本公司业务场景里说清楚怎么用——这是这一节的价值核心。
    市场机会型：≥ 2 顶级品类优秀做法（仅顶级品类，避免被细节淹没），可不填差异化风险。

[Spec 模板 1.8 节填充]

    | 来源产品/品类 | 借鉴维度 | 它的做法（具体描述） | 我们怎么用 | 借鉴后的差异化风险 |
    |---|---|---|---|---|
    | {{某产品 / 某品类做法}} | {{交互 / 增长 / AI / 工程 / 商业模式 / ...}} | {{具体怎么做，不是"很好"}} | {{要 / 不要 / 改造后用，落到我们哪块}} | {{照搬会丢什么差异，怎么补}} |
    | {{}} | {{}} | {{}} | {{}} | {{}} |

[不接受的答案]

    - "参考 Notion"——Notion 那么大，借鉴它什么？哪一点？落到我们哪？
    - "做得很好"——不可观察 = 不可借鉴
    - 只列借鉴对象不写"我们怎么用"——抄答案不是借鉴，是堆砌
    - 把同类产品改头换面塞进 1.8——那是 1.7 的活
    - 业务参照型只写"参考 X 公司的做法"不写落地——回退成标杆扫描 1.7，不是借鉴

---

[写入位置]

    Spec 模板：顶部填项目类型，1.5 系统功能架构之后填 1.7 标杆参考，再填 1.8 行业借鉴，再进 2. 功能范围。
    1.7 / 1.8 按项目类型的权重填了 Spec 才能发布。

[搜索增强]

    0-1 进场时先用 WebSearch 搜：
        - 业务参照型搜：主关键词 + "best practices" / "行业标准" / 同行案例 / 跨界关键词 → 行业借鉴素材为主
        - 市场机会型搜：主关键词 + "alternatives to X" / "X vs Y" / 行业报告 → 标杆扫描素材为主
    搜出来的前 5 个候选做粗筛：
        - 已在做同样事的进 Spec 1.7（同类产品 / 替代方案）
        - "某一块做得好"的进 Spec 1.8（行业借鉴）
    同一产品可能两边都进——它在 1.7 是做法来源，在 1.8 是某具体做法的借鉴来源，按角色分别填。

[触发条件]

    - 0-1 模式必走项目类型判断 + 标杆扫描 + 行业借鉴
    - 迭代模式（小功能）默认跳过，仅当用户主动说"我要挑战 XX / 看看行业怎么做"时触发
    - 主 Agent 可根据改动的范围与方向自行判断是否需要做行业借鉴
