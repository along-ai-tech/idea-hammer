# 原则：FRD 调研与逻辑严谨

> PRD 回答"做什么"，FRD 回答"具体怎么工作"。这一层靠拍脑袋最容易返工，必须先看别人怎么做、标准怎么写。

## 一、调研下限（每条 P0 REQ）

| 对象 | 数量 | 看什么 |
|---|---|---|
| 同类产品 | ≥ 2 | 同一功能怎么交互、怎么定义状态、怎么处理异常 |
| 业界实现 / 标准 | ≥ 2 | 官方文档、开放标准、成熟开源实现、平台 API 设计 |

记录格式（写进 FRD 的规则或状态下方，或该 REQ 的「调研记录」小段）：

```
来源：<名称> v<版本> <链接>（<查看日期>）
借鉴：<机制描述>
取舍：<直接采用 / 改造后用 / 不采用，理由>
```

约束：只允许引用能打开的来源；"业界最佳实践"不算来源；不复制实现代码，只提炼机制与约束。

## 二、逻辑严谨清单（写完 FRD 逐条自检）

- **状态全覆盖**：初始态、正常流转、失败态、超时/重试、终态；纯查询类显式写"无状态切换"
- **边界与非法输入**：空值、超长、越界、类型错误、重复提交
- **并发与幂等**：同一请求重复执行结果是否一致；并发写冲突怎么处理
- **权限与越权**：谁能做、能对谁做、跨用户/跨租户怎么拦
- **数据一致性与级联**：删除/更新时关联数据怎么办，失败是否回滚
- **错误契约**：错误码、提示语、是否可重试，前后端一致
- **可观测**：失败能否定位（日志/指标），不要求实现细节但要求可验证

## 三、与产品层竞品扫描的分工

- Phase 1.5 / 1.6 的竞品扫描：看"这个产品整体怎么解决这类问题"，服务于 §1.7 / §1.8
- 本原则的 FRD 调研：看"这个具体功能怎么工作"，服务于 §5 每个 REQ 的行为、规则、状态
- 两者不互相替代：产品层看过，不代表 FRD 层可以跳过

## 四、不合格信号

- 规则只有 MUST，没有边界与失败处理
- 状态只写正常路径，没有失败/超时/重试
- 写"参考业界最佳实践"但给不出来源
- 直接把某产品的交互抄进 FRD，却说不清为什么适合我们的场景
- 查询类功能不写排序、分页、权限范围，只写"返回列表"

## 五、产出

- 每条 P0 REQ 的「规则 / 状态」能回答：边界是什么、失败怎么办、并发怎么办、谁能做
- 调研来源与取舍写进 Spec，便于 code review 与后续迭代时追溯
