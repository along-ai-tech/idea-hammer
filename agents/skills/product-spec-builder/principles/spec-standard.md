# 原则：Spec 标准与 Phase 0 硬门禁

> 一句话需求能不能变成可执行的 Spec，取决于四要素是否齐全。
> 标准不是"写得好不好"，是"缺了就不准出关"。

## 〇、Spec 是唯一事实源

- code、test、accept、release 全部以 Spec 为输入：实现偏离 Spec 视为缺陷，不是"实现更合理"
- 需求变更必须先改 Spec 并记 CHANGELOG，再改代码；不允许"代码先上，文档后补"
- 测试的 `@trace` 指回 AC，AC 指回 REQ，版本发布清单引用 REQ —— 断链即视为 Spec 失真
- Spec 与下游文档（Design Brief / DEV-PLAN）冲突时，先修 Spec，再同步下游
- 任何"用户口头确认但 Spec 没写"的内容不生效；写进去才算数

## 一、四要素标准

### 1. PRD（为什么做 / 为谁做 / 什么价值）

| 必填项 | 最低要求 | 落在 Spec |
|---|---|---|
| 产品背景与目标 | 业务问题 + 具体损失 + 为什么现在 + 投入与替代方案比较 | §1.1 |
| 用户角色与画像 | ≥ 1 个具体角色 + 使用场景 + 现有习惯 | §1.2 |
| 用户核心问题 | 卡在哪一步 + 今天的凑合做法与代价 | §1.3 |
| 核心价值 | 一句可验证的 Before → After | §1.4 |
| 功能范围 | ≥ 1 条 P0 + ≥ 1 条 OUT（可标 [待定]，但不为空） | §2.1 / §2.2 |
| 核心业务流程 | ≥ 1 条 TASK + ≥ 1 条 FLOW | §3 |
| 产品优先级 | P0 / P1 汇总，与 §2、§5 一致 | §4 |
| 业务指标 | ≥ 1 个可计数或可观察的达标信号 | §1.6 |

### 2. FRD（每个功能怎么工作）

每条 P0 REQ 必须具备：

| 必填项 | 最低要求 |
|---|---|
| 目标 | 是什么 + 为什么 + 怎么做（三行齐） |
| 行为 | 触发 → 系统处理 → 产出的完整描述 |
| 规则 | ≥ 1 条 MUST / SHOULD，含边界 |
| 输入 / 展示字段 | 至少一类：输入逐字段给类型与校验，或展示字段给类型与可编辑性 |
| 输出 / 结果 | 成功与失败分别产出什么 |
| 状态 | 状态切换逐态列全；纯查询类显式写"无状态切换" |
| 调研记录 | ≥ 2 个同类产品 + ≥ 2 个业界实现 / 标准，含来源与取舍（见 frd-research.md） |

### 3. User Story（需求表达方式）

- 每条 REQ 至少 1 条，三句齐全：「作为一个 [角色]」「我希望 [完成某件事]」「以便于 [获得某种价值]」
- 角色必须来自 §1.2 的定义，不允许临时发明
- 一条故事只表达一个价值；"并且/同时"出现即拆分
- 通过 INVEST 自检：独立、可协商、有价值、可估算、足够小、可测试
- 不替代 FRD：故事说"要什么"，FRD 说"怎么工作"

### 4. AC（验收标准）

- 每条 REQ ≥ 3 条，覆盖主路径 / 边界 / 错误
- 格式 Given-When-Then，Then 给可观察结果，模糊词换数字
- 一条 AC 只验一个结果；出现"并且"就拆
- 禁用词：快速、友好、流畅、合理、尽量、适当——出现即重写
- 每条 AC 必须能被未来的一条 TEST 直接承接（可测性自检）
- 编号 `AC-<REQ 数字>-<两位序号>`，全局唯一，只增不改

## 二、Phase 0 硬门禁

分析需求时发现任一要素缺失或不确定，**必须在 Phase 0 处理掉**，三选一：

1. **变成具体追问**：一次最多 3 个阻塞问题，问法见 product-definition 五问
2. **变成显式假设**：可推断的写进 §10.1，带依据 + 猜错的后果
3. **变成开放问题**：不可推断的写进 §10.2，标阻塞 / 非阻塞

不允许的三种做法：
- 带着 `[待补充]` / `{{占位}}` / TODO 进 Design Brief 或 DEV-PLAN
- 用"看情况""先做出来再看"糊过去而不记录
- 自行扩展需求补缺口（比如替用户决定退款自动执行）

## 三、脚本校验（可自动化部分）

```bash
python3 scripts/check_spec_standard.py --project examples/personal-blog
```

校验内容：
- PRD 八个必填章节存在且无占位
- §1.2 / §1.6 / §2.1 / §2.2 有实质表格行；§3 有 TASK 与 FLOW
- 每条 P0 REQ：用户故事三句齐全；FRD 必备字段非空；AC ≥ 3 且编号与 REQ 匹配、全局不重复

不可自动化的部分（语义质量、追问是否到位）仍由 ceo-lens / eng-lens / qa-lens 自检覆盖。
脚本不通过 = Phase 0 不能出关，必须回到追问或登记假设。

## 四、与下游的关系

- 出口判据：脚本通过 + §9.1 全勾 + 阻塞问题清空（或被用户显式接受）
- 下游 DEV-PLAN 只接受通过门禁的 Spec；带缺口开工视为流程违规
