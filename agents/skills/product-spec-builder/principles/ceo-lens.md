# 原则：CEO 视角（Spec 收尾自检）

> 防"做完发现没人要/方向错"。gstack `/plan-ceo-review` 的轻量化版本。

[定位]
    主 Agent 写完 Product-Spec.md 收尾前，**显式切换提示词**跑这 4 问。
    不 spawn subagent——提示词切换 + 4 问清单足够。漏掉的进 Spec 10.2 待确认表。
    借鉴 gstack adversarial planning 哲学：同一份 Spec 不只让一种视角过。

[触发条件]
    - Spec 写完、收尾前必走
    - 迭代模式（小功能）跳过

[4 问]

    [1. v1 唯一成功指标]
        [覆盖意图]
            把 Spec 1.5 成功标准的多个指标压成 1 个——多 = 没指标。
        [自检问]
            "这份 Spec 的 v1 唯一成功指标是什么？不是注册量这种好刷的，是反映用户价值的。给我 1 个。"
        [不通过信号]
            - 列了 5+ 指标
            - 指标是注册量/下载量/DAU 这种虚荣指标
            - 说不清"用户用完后世界变好在哪"
        [补救]
            把 1.5 表砍到 1 行；其余降级为 P1 验证指标。

    [2. P0/P1 划分是不是"全 P0"]
        [覆盖意图]
            "全 P0" = 没优先级 = 团队永远疲于奔命 = 永远发布不出来。
        [自检问]
            "如果只能上线 1 个 P0、其余全砍，留哪个？现在 P0 列出来超过 5 个的，要砍。"
        [不通过信号]
            - P0 超过 5 个
            - 用户给不出"防御性"的砍法（"都重要、不能砍"）
        [补救]
            P0 上限 3-5 个；超过的按"用户拿不到会立刻弃用 vs 凑合能用"重排。

    [3. Phase 0 商业可行性 5 问过没]
        [覆盖意图]
            确保 business-context-check 的 5 问没被跳过/敷衍。
        [自检问]
            "5 问里用户回答最敷衍的是哪一题？是真敷衍还是真没想清楚？"
        [不通过信号]
            - 5 问里有 ≥ 1 题用户答"以后再想 / 看情况 / 想不到"
            - Q3 pre-mortem 用户没给 3 个失败原因
        [补救]
            把敷衍的那一题单独拎出来再追问一次；不行就进 Spec 10.2 待确认。

    [4. 1 年后回看会后悔漏记录什么]
        [覆盖意图]
            防御"写 Spec 时以为想清楚了，发布后才发现漏了一坨关键约束"。
        [自检问]
            "如果 12 个月后回看这份 Spec，最可能后悔'当时没记下来'的是什么？给我 1-3 件事。"
        [不通过信号]
            - 想不出任何东西（说明 Spec 真写完了，但要追问一次"真的吗"）
            - 列出来的全是细节 bug（说明 Spec 整体没问题，只是细节要补）
        [补救]
            提到的事补进 Spec（多半是 7.2 非功能需求 或 11 Agent 规格）。

[输出]
    4 问过完，写一段 ≤ 5 行的 [CEO 视角自检报告] 到 Product-Spec.md 末尾
    （在 11 Agent 规格之前或之后）。漏掉的进 10.2 待确认表。
