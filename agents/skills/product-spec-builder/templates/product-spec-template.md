## 0. AI 使用说明

- 本文档是产品功能、范围、行为和验收标准的事实来源。
- AI MUST 优先实现 P0。
- AI MUST NOT 实现“不在本版本范围”中明确排除的内容。
- AI MUST 根据“验收标准”判断功能是否完成。
- 如果信息不明确，AI MUST 使用“假设”中的假设；如果仍无法判断，应记录到“待确认问题”，而不是自行扩展需求。

| 字段 | 值 |

> 业务参照型 = 公司/团队已有业务方向，问题域成熟，重心在 1.8 行业借鉴。

> 类型未定 → 默认市场机会型，主 Agent 必须在生成 Spec 前向用户确认。

## 需求工程五层（本文档的组织方式）

| 层 | 回答什么问题 | 本文档对应位置 |
|---|---|---|
| 1. PRD | 为什么做、为谁做、提供什么价值 | §1–§4 |
| 2. FRD | 每个功能具体应该怎么工作 | §5 每个 REQ 的行为 / 规则 / 输入输出 / 状态 |
| 3. User Story | 用「作为…我希望…以便于…」表达需求，不是独立文档 | §5 每个 REQ 的用户故事 |
| 4. AC | 判断 User Story 或功能需求是否完成的可验证条件 | §5 每个 REQ 的验收标准（AC-###-##） |
| 5. Spec | 把以上内容组织成可执行的规格 | 全文 + 编号体系 + §9 完成定义 |

> 五层不是五份文档：PRD 与 FRD 是文档内容，User Story 与 AC 是表达与验收方式，Spec 是最终组织形态。

## 写作要点

1. **五层顺序**：PRD 定为什么做 / 为谁做 / 什么价值，FRD 定每个功能怎么工作，User Story 负责表达，AC 负责验收，Spec 把四者组织成可执行规格。缺任何一层都会让下游靠猜。
2. **AI 使用说明 / 完成定义**：这两节是给 AI 看的固定指令，按需微调，让 AI 判断范围和完成。
3. **PRD（§1–§4）**：锁定一类具体主用户 + 一个有时间地点的真实问题实例 + 量化代价；核心价值一句话；业务指标要能数出来，不用注册量这类虚荣指标。0.5 项目类型决定 1.7 / 1.8 的填充权重（业务参照型 vs 市场机会型），类型未定必须先确认才能往下走。
4. **功能范围**：本版本做的和不做的都给编号、标 P0/P1；至少 3 条显式非目标，说不出说明范围没想清。
5. **核心业务流程**：先列用户任务 TASK（独立于功能怎么实现，一个 TASK 可对应多个 REQ），再用 FLOW 走端到端主路径、分支、边界与完成状态。
6. **产品优先级**：§4 汇总 SCOPE / REQ 的 P0/P1，与 §2、§5 保持一致；P0 必须本版本完成并验收。
7. **FRD 功能需求 REQ**：关联 TASK / FLOW；行为写清触发 → 系统 → 产出；规则用 MUST / SHOULD；输入逐字段写类型和校验；状态五态逐一，空态不等于错误态。
8. **User Story**：每个 REQ 用「作为一个 [角色] / 我希望 [完成某件事] / 以便于 [获得某种价值]」表达；它是需求表达方式，不单独成文档，也不能替代 FRD 的行为细节。
9. **AC 验收标准**：判断 User Story 或功能需求是否完成的可验证条件，写成 Given-When-Then，Then 给具体可观察结果，模糊词换数字；每条 AC 用 `AC-<REQ>-<nn>` 唯一编号，主路径 / 边界 / 错误至少各一条。
10. **AI 能力规格**：每个 AI 功能补质量条、触发方式（建议 / 自动）、不确定时行为、服务降级，单列护栏写明绝不能做什么。AI 是概率性的，不钉死就是赌。
11. **数据模型**：核心实体 + 关系 + 数据规则（创建 / 更新 / 删除 / 权限）；纯前端产品可略。
12. **外部依赖 / 非功能**：依赖标是否必需；非功能 6 类逐项给数字或断点、标 P0 / P1。
13. **假设与待确认**：信息不全时能推断的写假设（带依据和错误风险），不能判断的写待确认，别自行扩展需求。
14. **Agent 系统规格**：仅当产品本身是 agent / 自主系统时填，覆盖自主性 / 工具 / 上下文 / 编排 / eval / 成本 / 失败 / 状态。
15. **跨文档一致**：编号 ID（SCOPE / TASK / FLOW / REQ / AC）供 Design Brief、DEV-PLAN、测试注释引用，两边 P0 内容保持一致；ID 只增不改，需求废弃标 `[已废弃]` 而不复用编号。
16. **文档元信息表**：每次更新 Spec 必须更新顶部元信息表。
17. **图必填**：架构图（§1.5）所有 Spec 必填；流程图（§3 用户流程）必填；状态图（§5 REQ 状态流转）含状态切换的 REQ 必填。
18. **"是什么 / 为什么 / 怎么做"**：§1.1 产品背景与目标 + §5 REQ 目标统一格式，Phase 1/4 采访已有素材可直接填。
19. **展示 vs 输入**：§5 REQ 区分两类字段，分别喂下游设计稿与开发。
20. **状态流转**：必填的 REQ 类型 = 含状态切换；纯展示类跳过。
21. **并发与一致性**：按 0.5 类型路由（单机允许"不要求"；联网服务必填）。
