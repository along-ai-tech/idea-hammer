# 产品需求规范：{{产品名称}}

## 0. AI 使用说明

- 本文档是产品功能、范围、行为和验收标准的事实来源。
- AI MUST 优先实现 P0。
- AI MUST NOT 实现“不在本版本范围”中明确排除的内容。
- AI MUST 根据“验收标准”判断功能是否完成。
- 如果信息不明确，AI MUST 使用“假设”中的假设；如果仍无法判断，应记录到“待确认问题”，而不是自行扩展需求。

## 0.5 产品类型（驱动竞品扫描与范围权重）

| 字段 | 值 |
|---|---|
| 项目类型 | `{{业务参照型 / 市场机会型}}` |
| 判断依据 | {{为什么是这一类：公司既有业务线 / 用户主动说"参考 XX" / 市场窗口未定型 / ...}} |

> 业务参照型 = 公司/团队已有业务方向，问题域成熟，重心在 1.7 行业借鉴。
> 市场机会型 = 用户痛点未充分满足，重心在 1.6 竞品扫描 + 差异化判断。
> 类型未定 → 默认市场机会型，主 Agent 必须在生成 Spec 前向用户确认。

## 写作要点

1. **AI 使用说明 / 完成定义**：这两节是给 AI 看的固定指令，按需微调，让 AI 判断范围和完成。
2. **产品上下文**：锁定一类具体主用户 + 一个有时间地点的真实问题实例 + 量化代价；核心价值一句话；成功标准要能数出来，不用注册量这类虚荣指标。0.5 项目类型决定 1.6 / 1.7 的填充权重（业务参照型 vs 市场机会型），类型未定必须先确认才能往下走。
3. **范围**：本版本做的和不做的都给编号、标 P0/P1；至少 3 条显式非目标，说不出说明范围没想清。
4. **用户任务 TASK**：用户要达成的目标，独立于功能怎么实现；一个 TASK 可对应多个 REQ。
5. **用户流程 FLOW**：关联 TASK，主路径分步、标出分支和边界情况、写清完成状态。
6. **功能需求 REQ**：关联 TASK / FLOW；规则用 MUST / SHOULD；输入逐字段写类型和校验；状态五态逐一，空态不等于错误态；验收写成 Given-When-Then，Then 给具体可观察结果，模糊词换数字。
7. **AI 能力规格**：每个 AI 功能补质量条、触发方式（建议 / 自动）、不确定时行为、服务降级，单列护栏写明绝不能做什么。AI 是概率性的，不钉死就是赌。
8. **数据模型**：核心实体 + 关系 + 数据规则（创建 / 更新 / 删除 / 权限）；纯前端产品可略。
9. **外部依赖 / 非功能**：依赖标是否必需；非功能 6 类逐项给数字或断点、标 P0 / P1。
10. **假设与待确认**：信息不全时能推断的写假设（带依据和错误风险），不能判断的写待确认，别自行扩展需求。
11. **Agent 系统规格**：仅当产品本身是 agent / 自主系统时填，覆盖自主性 / 工具 / 上下文 / 编排 / eval / 成本 / 失败 / 状态。
12. **跨文档一致**：编号 ID（TASK / FLOW / REQ）供 Design Brief 引用，两边 P0 内容保持一致。
13. **文档元信息表**：每次更新 Spec 必须更新顶部元信息表。
14. **图必填**：架构图（§1.4.1）所有 Spec 必填；流程图（§4 用户流程）必填；状态图（§5 REQ 状态流转）含状态切换的 REQ 必填。
15. **"是什么 / 为什么 / 怎么做"**：§1.1 产品摘要 + §5 REQ 目标统一格式，Phase 1/4 采访已有素材可直接填。
16. **展示 vs 输入**：§5 REQ 区分两类字段，分别喂下游设计稿与开发。
17. **状态流转**：必填的 REQ 类型 = 含状态切换；纯展示类跳过。
18. **并发与一致性**：按 0.5 类型路由（单机允许"不要求"；联网服务必填）。
