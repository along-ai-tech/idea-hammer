# 流程：生成 Technical Design

> 先定方案再排计划。技术设计没收敛，不进入 DEV-PLAN。

## 阶段 1：加载输入

**动作**：
1. 读 Product-Spec.md：范围、NFR、核心数据、外部依赖
2. 读 Design-Brief.md：页面、交互与状态（仅取影响接口与数据结构的约束）
3. 读现有代码、配置与工程约束（`_engineering-constraints/`）
4. 向用户确认规模预期、团队与部署条件

**完成**：输入齐全；缺 Product Spec 先退回 product-spec-builder

## 阶段 2：架构决策

**动作**：
1. 按约束列出 2–3 个候选架构模式（单体 / 模块化单体 / 微服务 / 事件驱动叠加）
2. 逐项写优势、代价、触发条件，默认选满足约束的最低复杂度
3. 用户确认后写 ADR：背景、决策、备选、权衡、后果、重评估触发
4. 画架构图：部署单元、模块、外部依赖、数据流

**完成**：模式选定，架构图与 ADR-001 落地

## 阶段 3：模块与领域建模

**动作**：
1. 按业务能力划模块，写职责、对外接口、允许依赖
2. 校验依赖单向、无循环；跨模块不直连对方数据表
3. 识别实体、值对象、聚合与限界上下文
4. 为每个聚合写不变量，并说明并发下由谁守住

**完成**：模块边界与领域模型可映射到数据设计

## 阶段 4：数据设计

**动作**：
1. 出表结构：字段、类型、主键、外键、唯一约束
2. 按查询路径设计索引，写组合顺序
3. 定事务边界、并发控制、软删除、审计字段、版本化策略、多租户隔离
4. 写迁移与回滚策略

**完成**：数据设计逐项表态，无「表名 + 用途」式占位

## 阶段 5：API Contract

**动作**：
1. 列端点：方法、路径、权限、请求/响应字段、错误码、幂等
2. 定基础路径、鉴权、统一错误体、版本策略
3. 生成 OpenAPI（或明确 Contract 载体），前端按 Contract Mock
4. 写契约测试范围与 Contract 变更流程

**完成**：Contract 可供前后端并行开发，不靠口头约定

## 阶段 6：风险与非功能

**动作**：
1. 按性能、安全、可用性、可观测性写实现方式与验证方式
2. 列风险：影响、概率、缓解、触发信号、兜底
3. 高风险项转为 DEV-PLAN 的 spike 或前置验证任务

**完成**：风险有缓解与兜底，不只列现象

## 阶段 7：输出与自检

**动作**：
1. 按 templates/technical-design-template.md 输出 `Technical-Design.md`
2. 自检：架构图、模块边界、聚合不变量、数据约束、API Contract、ADR、风险、Phase 映射
3. 用户确认后交 workflow-generate.md 拆 DEV-PLAN

**完成**：Technical Design 可执行、可追踪、可映射到 Phase
