# 原则：技术设计与架构决策

> Product Spec 说明「做什么」，Design Brief 说明「长什么样」，Technical Design 说明「怎么实现」，DEV-PLAN 说明「按什么顺序做」。四份产物各司其职，缺了第三份，代码阶段就只能靠即兴发挥。

## 一、四份产物的边界

| 产物 | 回答 | 不回答 |
|---|---|---|
| Product Spec | 为谁解决什么问题、范围、行为、验收标准 | 用什么技术、怎么部署 |
| Design Brief | 页面、组件、交互、视觉与状态 | 后端结构、数据表、接口 |
| Technical Design | 系统架构、模块边界、领域模型、数据设计、API Contract、技术决策与风险 | 具体写哪个文件、任务排到第几周 |
| DEV-PLAN | 分几个 Phase、每个任务改哪些文件、先做什么、怎么验证 | 重新论证架构与选型 |

Technical Design 与 DEV-PLAN 可以互相迭代，但不能混写：前者是方案，后者是执行顺序。架构变了先改 Technical Design，再改 DEV-PLAN。

## 二、输入与出口

**输入**：Product Spec（范围、NFR、数据模型、外部依赖）、Design Brief（页面与交互）、现有代码与约束、规模与并发预期、团队与部署条件、合规要求。

**出口（全部满足才算完成）**：

- 架构模式已选定，并有一张架构图（部署单元、模块、外部依赖、数据流）
- 模块边界与依赖方向明确，模块之间不直接跨库读写
- 领域模型含实体、值对象、聚合、限界上下文与聚合不变量
- 数据库设计含表、主外键、唯一约束、索引、事务边界、并发控制、软删除与审计字段的决策
- API Contract 含端点、请求/响应字段、错误码、权限、幂等、版本与 Mock 策略
- 至少一条 ADR，写清备选方案与否决理由
- 风险表含影响、缓解与触发信号
- 能映射到 DEV-PLAN 的 Phase 与任务

## 三、架构模式选择

| 模式 | 适合 | 代价 |
|---|---|---|
| 单体 | 单团队、单部署、边界尚未稳定 | 模块纪律靠人守，容易长成泥球 |
| 模块化单体 | 中小团队、边界清晰但不需要独立部署 | 需要明确的模块接口与依赖规则 |
| 微服务 | 多团队独立交付、按服务独立扩容或隔离故障 | 分布式事务、可观测性、运维成本显著上升 |
| 事件驱动 | 异步解耦、削峰、跨模块最终一致 | 幂等、重试、顺序与可追踪性复杂度上升 |

决策顺序：**先约束，后模式**。默认选满足约束的最低复杂度方案；小团队内部系统优先模块化单体。以下条件同时出现两个以上才考虑拆服务：独立扩容需求、独立发布节奏、团队边界清晰、故障需要隔离。事件驱动是解耦手段，可以叠加在任何模式上，不单独作为拆分理由。

禁止「因为流行」选型。没有量化的扩容、隔离或组织理由，不拆微服务。

## 四、模块与领域建模

- 模块按业务能力划分，不按技术层划分；每个模块写职责、对外接口、允许依赖的模块
- 依赖方向单向，禁止循环依赖；跨模块只能走公开接口
- 领域模型先识别概念，再决定用 Entity、Value Object、Aggregate 还是 Bounded Context，不为 DDD 而拆
- 聚合要写不变量：什么条件必须始终成立、由谁保证、并发时如何守住
- 聚合之间用 ID 引用，不直接持有对方实体
- 限界上下文之间明确映射关系（共享内核 / 客户-供应商 / 防腐层）

## 五、数据库设计

设计阶段至少对以下项逐条表态，不适用的写原因：

| 项 | 要写清 |
|---|---|
| 主键 | 类型、生成方式（自增 / UUID / 雪花） |
| 外键与级联 | 是否启用、删除策略（CASCADE / RESTRICT / SET NULL） |
| 唯一约束 | 业务唯一键，不能只靠应用层判断 |
| 索引 | 查询路径、组合顺序、是否覆盖 |
| 事务边界 | 一次事务包含哪些写操作，跨聚合如何处理 |
| 并发控制 | 乐观锁版本号 / 悲观锁 / 唯一约束兜底 |
| 软删除 | 是否需要、如何过滤、唯一键如何兼容 |
| 审计字段 | created_at / updated_at / created_by |
| 版本化与不可变 | 哪些数据只增不改，参考 `_engineering-constraints/database/versioning-and-immutability.md` |
| 多租户 | 租户键、隔离级别、越权查询防护 |

表结构以 DDL 或字段表呈现，不能只写「表名 + 用途」。迁移策略（初始化 / 增量 / 回滚）一并说明。

## 六、API Contract

Contract 先于实现：

1. 先写端点、请求与响应字段、错误码
2. 生成 OpenAPI（`_engineering-constraints/api-design/openapi-required.md`），作为唯一事实源
3. 前端按 Contract 做 Mock，后端并行实现
4. 契约测试校验实现与 Contract 一致
5. 联调只修实现，不偷偷改 Contract；要改先更新 Contract 并通知使用方

每个端点写清：方法、路径、权限、请求字段与类型、响应字段、错误码、是否幂等、版本策略。

- 错误响应统一结构，业务错误码可枚举
- 写操作说明幂等键或天然幂等条件
- 版本策略二选一并写死：URL 版本（`/api/v1`）或只增不改 + 破坏性变更升版本
- 鉴权方式、未登录与无权限的返回码提前定义

## 七、ADR

影响架构、数据模型、接口契约或外部依赖的决策，一条一个 ADR：

| 字段 | 内容 |
|---|---|
| 编号 / 标题 | ADR-001 选择模块化单体 |
| 状态 | proposed / accepted / deprecated / superseded |
| 背景 | 约束、规模、团队、时间 |
| 决策 | 选了什么 |
| 备选方案 | 还考虑过什么，为什么否决 |
| 权衡 | 放弃什么、换来什么 |
| 后果 | 对代码、运维、后续迭代的影响 |
| 重评估触发 | 什么信号出现时重新讨论 |

技术选型先查既有方案与标准库（Anti-Reinvent），再用 WebSearch 核实版本、维护状态与已知漏洞；给出 2–3 个候选让用户拍板，不替用户默认。

## 八、风险

| 字段 | 内容 |
|---|---|
| 风险 | 可能发生什么 |
| 影响 | 对进度、数据、安全、成本的影响 |
| 概率 | 高 / 中 / 低 |
| 缓解 | 提前做什么 |
| 触发信号 | 出现什么现象说明风险成真 |
| 兜底 | 成真后怎么退 |

高风险项在 DEV-PLAN 里安排验证性任务（spike），不要拖到联调才暴露。

## 九、不合格信号

- 只有技术栈表，没有架构图与模块边界
- 选型只有结论，没有备选与权衡
- 数据设计只有表名，没有约束、索引与事务
- API 只有路径，没有字段、错误码与版本
- 领域模型是所有表的一对一映射，没有不变量
- Technical Design 直接写成了任务清单
