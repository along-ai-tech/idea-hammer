# 流程：调试四阶段（根因调查 → 复现测试 → 假设验证 → 实施修复）

> 无根因调查不下药方，无失败复现测试不准改生产代码。

## 阶段 1：根因调查

**目标**：找到根因，不是表象
**动作**：
1. 完整报错和 stack trace
2. 复现步骤（用户输入 → 系统响应）
3. 环境信息（OS / 运行时版本 / 依赖版本）
4. 最近的代码变更（git log / git diff）
5. 相关日志（加诊断日志：进什么 / 出什么 / 状态如何）

**完成**：bug 能稳定复现

**bug 不能稳定复现**：先收集更多数据，**不准猜**

**多组件系统**：每个边界加诊断日志

## 阶段 2：复现测试

**目标**：写失败测试当修复的"契约"
**动作**：
1. 写一个最小失败测试复现 bug
2. 跑测试确认它 FAIL
3. 确认失败原因对（功能缺失，不是笔误）

**完成**：测试 FAIL 且原因合理

**注意**：bug 涉及服务状态时，先 kill 占用端口的进程再调试（多实例是很多灵异 bug 的根因）

## 阶段 3：假设与验证

**目标**：列假设、验假设
**动作**：
1. 基于根因列假设
2. 一次最多 3 个，按可能性排序
3. 每个有验证方法
4. 先验最可能的
5. 否定了记原因不重复验

**完成**：定位真正原因

## 阶段 4：实施修复

**目标**：一次一个逻辑点修完 + 验证
**动作**（每改一处循环）：
1. 一次一个逻辑点
2. 编译验证：tsc --noEmit 零错误
3. 原复现测试 PASS
4. 跑全套测试零失败
5. 回归相关功能正常

**失败处理**：
- 修复失败 → 回退重新假设
- 连续 3 次失败 → 停下重审（不是代码层面问题）

## 完成后

1. 汇报：根因 / 改动 / 编译和回归证据
2. 问要不要 commit，message 用 `fix:` 前缀
3. 用户直接报 bug：建议 /code-review 验证
4. code-review Stage 2 报出：主 Agent 重派 code-review 从 Stage 1 起
