# 原则：测试金字塔与不变量门禁

> TDD 不等于所有逻辑都写单元测试。按层选验证手段；业务不变量必须在真实执行环境里成立。

## 五层验证

| 层级 | 验证什么 | 典型写法 | 什么时候必须有 |
|---|---|---|---|
| Unit Test | 单个函数、领域规则、边界条件 | `test_duplicate_grant_rejected` | 有分支、有规则判断的逻辑 |
| Integration Test | 模块与基础设施协作 | 数据库约束、事务、跨模块调用 | 碰数据库 / 队列 / 缓存 / 外部服务 |
| Contract Test | 接口契约一致性 | 响应符合 Schema、错误码对齐 | 前后端分离、API 被外部调用 |
| E2E Test | 完整用户流程 | 管理员完成授权并看到结果 | 核心链路（每个 Phase 至少一条） |
| Regression Test | 原有功能未被破坏 | 老测试全绿、老数据仍可读 | 任何改动后必须跑全套 |

分层要求：

- **Unit 快而多**：边界（空、零、nil、未授权、畸形输入）必须有
- **Integration 少而准**：只在单测测不到的地方加
- **Contract 与 E2E 贵**：每个 Phase 至少各覆盖一条核心路径，不铺开
- **Regression 不省**：改完跑全套，不是"跑相关的那几个"

## 并发竞态门禁（本模块最高优先级）

单元测试通过 ≠ 业务安全。典型的 check-then-act 竞态：

```
请求 A：检查不存在
请求 B：检查不存在
请求 A：插入
请求 B：插入   ← 重复记录
```

只要业务规则里有"不允许重复"（唯一授权、唯一注册、幂等创建），必须三件套齐全：

1. **单元测试**：重复调用被拒绝（业务规则层）
2. **数据库唯一约束**：把不变量下沉到存储层兜底
3. **并发测试**：两个请求同时打进来，只有一个成功

只做第 1 条 = 竞态仍然存在；只做第 1、2 条而不做第 3 条 = 并发路径从未被验证过。

其他触发并发门禁的场景：库存扣减、余额变更、状态机流转、计数与点赞、配额占用。

## Invariant 与 Regression 的区别

- **Invariant（不变量）**：任何合法执行路径都必须始终成立。例如"一个 Tool 不允许被重复注册"
- **Regression Test（回归测试）**：验证这次修改没有破坏既有行为

一个不变量通常需要多条测试共同保证：单元测试（规则）+ 数据库约束（存储）+ 并发测试（时序）+ 回归测试（既有路径）。

## 每 Task 的测试产出要求

1. RED：先写失败测试，覆盖本 Task 每个行为点，每条带 `@trace TEST-### REQ-###/AC-###-##`
2. GREEN：最小实现，全套绿
3. REFACTOR：不新增行为，仍全绿
4. 收尾：跑全套测试（Regression），不是只跑本 Task 新增的

缺哪层就补哪层。判断依据是"这层能测出单测测不到的问题吗"，能就写，不能就记理由跳过。
