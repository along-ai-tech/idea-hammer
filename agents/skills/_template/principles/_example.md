# 原则：示例 — 范围纪律

> 只动当前 Phase 和 Task 范围内的东西。范围外的不碰，哪怕 Spec 里写了该行为。

## 为什么

跨范围改动会让 Phase 边界模糊、依赖关系不可控。代码和 Spec 脱节比晚交付更难补救。

## 怎么做

1. 接到任务时先读 DEV-PLAN.md 确认当前 Phase / Task 范围
2. 改动前自问："这个改动在不在当前 Task 里？"
3. 不在 → 拒绝执行，提示用户开新 Phase 或新 Task
4. 在 → 改完跑当前 Task 的验证（测试 + typecheck）

## 反模式

- ❌ "顺手把这个 bug 也修了" → 跨范围改动，进 review 时回退
- ❌ "Spec 里写了但没排进 Phase，先做了" → 越权推进度
- ❌ "反正都是同一文件，一起改完" → 让单次 commit 不止一个目的
